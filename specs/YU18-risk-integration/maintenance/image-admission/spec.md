# Intended image admission specification

Status: implemented offline; live deployment and registry attestation remain unverified. Owner: Codex RI20. State: YU18-risk-integration, parent YU17-otc-rates. Authoritative tooling is under `scripts/yu15/`; component documentation is copied by the YU18 renderer into generated spec-source. Existing runtime/deployment generation inputs stay in their state parents.

## Requirements

- FR-IA01: Read structured rendered Kubernetes resources. Cover Deployment, StatefulSet, DaemonSet, ReplicaSet, ReplicationController, Job, CronJob and Pod container, init-container and ephemeral-container slots. Expand Kubernetes Lists. Empty populations, duplicate identities and unknown image-bearing resource kinds refuse. Labels, annotations and arbitrary text mentioning an image are not image references.
- FR-IA02: Require an independent expected plan for the explicit target, selected state, selected manifest owner and every rendered slot. The rendered image must exactly equal the expected immutable repository digest. Tags, image IDs alone and a state-derived name are insufficient. One digest cannot have conflicting expected ownership.
- FR-IA03: Require explicit component owner/source/generated paths and bounded hashes. Each artifact names its intended `buildState`, which may be an ancestor deliberately selected by a newer deployment. The owner must be the final runtime-override layer for that component within the explicit build-state ancestry, not automatically the deployment state. Inherited components are admitted deliberately; selecting the newest state does not attest their payloads. Runtime overrides compose last-wins; the generated component hash covers the resulting complete context, not only the owner's partial override directory.
- FR-IA04: Consume a sealed offline inspection and separately reviewed content report. Match immutable repository ref, config image ID, OS/architecture, payload entry hashes, source ownership and canonical provenance hash. Unknown producers and missing/malformed metadata refuse with a reason. A missing artifact is not silently replaced with an ancestor or synthetic proof image.
- FR-IA05: Support `ri18-fix-v1` only for the generated order-matcher component. Reuse RI18's selected source, composition, recipe and patch fingerprint and payload canonicalization. Require its complete supported provenance shape and unmodified fix-role content. STP pre/disabled payloads refuse regardless of the external provider's declarations. RI18 does not attest every service.
- FR-IA06: Support `reviewed-artifact-v1` as a trusted local per-component reviewed report consumer, not an automatic service build producer. Require explicit bounded generation-input hashes, reviewed immutable artifact binding and positive assertions for immutable reference, packaged payload and source mapping. Evidence is supplied independently by the operator/reviewer. The helper never derives expectations from running pods or manufactures missing production provenance.
- FR-IA07: Before every proof preparation, require the baseline repository reference to resolve in structured CRI inventories on every parsed kind node, independently of rebuild. Recheck proof-selected images before rebuild destruction. A tagless blob, wrong tag, different repository digest alias or current pod imageID cannot satisfy reference resolution. Ambiguous/empty/malformed inventories refuse. No node-store repair occurs.
- FR-IA08: Require explicit GKE context, project, location, cluster, namespace, selected state and manifest owner. Bind these to the expected plan; no ambient/default GCP project selection. Default execution renders/validates offline. Separate apply uses the admitted snapshots with the operative selected-lineage database schema before workloads. Local kustomize resource/patch/generator file closure is checked before rendering; remote paths, plugins and Helm refuse. Input hashes are rechecked after rendering.
- NFR-IA01: Inspect-only render/admission calls no cloud/cluster/image-store mutation or cluster discovery. Refusals occur before preparation/supervisor cleanup writes or GKE apply. Use installed parsers or stdlib JSON; no network dependency installation.
- NFR-IA02: Preserve RI17 supervision, explicit reset authorization and separately reviewed retained compatibility. Admission reports explicitly say compatibility and node availability were not assessed and operator authorization was not inferred. A successful image check does not qualify a mixed-core rollout, migration, rollback, storage reset, financial result or performance claim.

## Explicit artifact contract

`traderx-intended-deployment-v1` is an operator/reviewer supplied JSON object with:

- `target`: exact `context`, `project`, `location`, `cluster`, `namespace`. The context must be `gke_<project>_<location>_<cluster>` and agree with the CLI. This is a declarative offline target binding, not live endpoint or kubeconfig authenticity verification.
- `state` and `manifestPack`: catalog IDs; the manifest pack must be in the selected state's ancestry. No highest-folder guess selects the state.
- `slots`: a nonempty object keyed by `namespace/kind/workload/containerGroup/containerName`. Every image-bearing rendered slot must be present and no absent workload may be expected.

Each slot value has `reference` (exact `repo@sha256:<64 hex>`), `component`, `buildState`, `ownerState`, `role` (`production`), `provider` (`ri18-fix-v1` or `reviewed-artifact-v1`), `platform` (`linux/amd64` or `linux/arm64`), `sourcePath`, `generatedPath`, `ownerSha256`, `sourceSha256`, `payloadSha256`, `provenanceSha256`.

`sourcePath` is `specs/<ownerState>/generation/runtime-overrides/<component>`; `generatedPath` is a bounded `generated/.../code/target-generated/<component>` path; the default current context is `generated/code/target-generated/<component>`. An intentionally inherited build can use a separately generated ancestor context. Both `buildState` and `ownerState` must be in deployment ancestry, with the owner operative for that build state. Tree hashes use the accepted RI18 exact-path/byte/executable-bit hash, excluding only its top-level build/.gradle/.git outputs. Provenance and payload hashes use RI18 canonical JSON. External reviewed producers may declare the entire pipeline directory as a conservative generation input. Inputs and partial owner trees are evidence of build mapping, not retained reader compatibility.

`traderx-offline-image-inventory-v1` contains an `artifacts` array. Each item repeats the expected identity fields and adds:

- `inspection`: a Docker-style immutable `Id`, `RepoDigests`, `Os`, `Architecture`, `Config.Labels`. A config ID is distinct from a repository manifest digest. The expected repository digest must appear in `RepoDigests`.
- `payloadEntries`: a nonempty list of unique `[relativePath, sha256]` pairs captured from inspected packaged bytes, sorted for hashing. RI18 payloads include classes/resources and dependencies.
- `review`: repository-independent evidence `path` relative to the inventory directory and exact-byte `sha256`. Paths cannot escape that directory.

For RI18 fix provenance, `dev.traderx.stp.provenance` must carry the accepted `traderx-stp-image-v1` shape, role `fix`, the selected fingerprints, role source hash and packaged payload hash. Source revision is recorded history; it is not substituted for byte identity. The RI18 adapter retains its existing fixed current generated context path; other separately mapped ancestor contexts use the reviewed external provider. Captured toolchain and resolved base inputs remain part of the independently expected canonical provenance and reviewed binding. This offline consumer does not reinspect the host builder or registry.

For the reviewed external provider, `dev.traderx.image.provenance` is JSON with schema `traderx-reviewed-image-v1`, all identity fields except provider/provenanceSha256, and nonempty unique `generationInputs` entries with bounded repository `path` and `sha256`. It is a supported supplied attestation contract; RI20 does not add this label to service images or assume old builders already emit it. Vendor/runtime images without a mapped context and supported review refuse until an appropriate producer contract is supplied.

The content review JSON uses schema `traderx-intended-image-review-v1`, verdict `verified`, nonempty `reviewedBy`, positive integer `assertions`, and boolean true checks `immutableReference`, `packagedPayload`, `sourceMapping`. Its `artifact` must exactly bind `reference`, inspected `imageId` and every expected identity field. Matching file hashes establish exact local evidence custody; they do not authenticate the reviewer or registry. Fixture reviews are explicitly synthetic.

## Acceptance scenarios

- SC-IA01: Matching explicit intended component and deliberately inherited component admit; wrong state, component, role, owner, platform and shadowed owner refuse.
- SC-IA02: Missing ref on one node, tagless content, wrong repository/tag, ambiguous records and malformed/empty inventory refuse before rig writes even if all fixture pods are running and no rebuild would be needed.
- SC-IA03: Missing/malformed provenance, unsupported producer, mutable rendered image, omitted init container, empty assertions and readiness-only evidence refuse through actual GKE startup, including its fake apply path with zero mutations.
- SC-IA04: Accepted RI18 actual offline builder output supplies an explicit fix artifact; changed composition, malformed RI18 shape and pre payload refuse. Content identity never supplies retained compatibility.
- SC-IA05: Render real installed local kustomize manifests, enumerate actual slots, and record refusal for current mutable pins. Generate YU18 and verify component docs/source mapping. These are source/generated/offline controls, not live deployment acceptance.
