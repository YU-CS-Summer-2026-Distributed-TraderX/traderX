# Member readiness diagnostics specification

Status: implemented and locally verified; coordinator review pending. Owner: Codex RI23. Base: `a0d6da0bfbef481f301bb1172b6810cb8a4c9e3e`. Interface: additive member `/ready` JSON. Dependencies: existing member `/health` and Jackson dependencies; no new service or state format.

- FR-RD01: Preserve `ready`, legacy `applied`/`maxPeerApplied`, startup `reason`, HTTP readiness status, the exact legacy readiness expression, 5000 default tolerance, 250 ms sleep between passes and 300 ms peer connect/read timeouts. Liveness, routing configuration, consensus policy and core/wire/snapshot formats remain unchanged.
- FR-RD02: Report configured peer-slot count, valid observation count, unavailable count and `not_sampled`, `none_configured`, `unavailable`, `partial` or `complete` coverage. Slots come from the existing hostname list excluding the member index; responses are not authenticated or deduplicated member identities. Zero configured peers distinguishes configured single-member use from configured peers with no observations. It does not prove the actual deployment size.
- FR-RD03: Report `maxObservedPeerApplied`, nonnegative `observedLag`, `configuredMaxLag`, nullable `withinLagTolerance` and nullable `caughtUpToObservedSequence`. Comparisons require a started local engine, nonnegative local applied sequence and at least one valid nonnegative peer JSON integer. Zero is a valid reading. A present `started` must be boolean `true`; boolean `false` or any nonboolean value, including JSON null, is unavailable. A missing field retains compatibility with applied-sequence-only responses. Malformed, duplicate-key, trailing-data, fractional, string, overflow, missing or negative readings cannot certify diagnostic catch-up. A negative configured tolerance makes the diagnostic tolerance comparison unknown while preserving legacy routing arithmetic.
- FR-RD04: Provide local wall-clock `sampleStartedAtEpochMs` and `sampleCompletedAtEpochMs`. Initial cache timestamps and observation counts are null. A cold engine reports `not_sampled`, unavailable local sequence and unknown comparisons, even after its sampling timestamps exist. The response scope is `maximum_observed_applied_sequence`.
- NFR-RD01: Diagnostics run on the existing cold sampler; add no peer requests, policy decisions, watchdog, daemon, hot-path writes or financial calculations. Keep RI20 scripts and RI22 metrics separate.
- NFR-RD02: Document sequential, racy observations and cached freshness. No sequence-only convergence, quorum, same-book, leader-eligibility, restart-safety, HA, performance or financial assertion is exposed.

## Fields and interpretation

`configuredPeerCount` counts hostname slots except this member. `observedPeerCount` counts slots whose response supplied a valid nonnegative JSON integer; `unavailablePeerCount` is configured minus observed. Both observation counts are null before peer sampling or while the local engine is absent. Unavailable combines transport failure, absent/uninitialized readings and invalid responses; it does not diagnose a partition.

`maxPeerApplied` retains the legacy integer-regex parse for compatibility and readiness. `maxObservedPeerApplied` is the maximum validated JSON integer, or null without observations. They may differ: the old regex accepts an integer prefix in fractional/malformed text and ignores whitespace after the colon. Those legacy inputs retain their old routing verdict while diagnostics honestly reject invalid JSON or recognize a valid spaced integer. Diagnostics never override that routing verdict.

With valid local/peer readings, `observedLag = max(0, maxObservedPeerApplied - applied)`, `withinLagTolerance = observedLag <= configuredMaxLag` for nonnegative tolerance, and `caughtUpToObservedSequence = applied >= maxObservedPeerApplied`. Thus Ready can coexist with false caught-up, partial coverage, or unknown comparisons. An ahead-of-peer local sequence yields zero lag. None of these flags compares books or establishes quorum.

Sample timestamps mark one pass on the member's wall clock. The local sequence is read before peer requests; peers are queried sequentially and may change while sampling. The cached result can already be old when returned. Pass duration includes requests; 250 ms is the sleep after a pass, not a freshness bound. Exceptions retain the previous cache with its old timestamps. Compare timestamps only with clock-skew/clock-adjustment awareness; they provide no synchronized cut, monotonic duration guarantee or hard expiry. The existing separate status/body atomic publications can transiently represent different passes; this change does not redesign publication.

## Acceptance scenarios

SC-RD01: original production handler reproduces Ready with configured but unobserved peers and no diagnostic differentiation. SC-RD02: startup/cache and absent engine yield unknown comparisons. SC-RD03: no configured peers versus configured but unavailable peers. SC-RD04: partial versus full valid observations at equal sequences. SC-RD05: lag exactly 5000 is Ready but not caught-up; lag 5001 preserves 503; ahead-of-observed peer has zero lag. SC-RD06: negative/missing/malformed/fractional/string/overflow/duplicate/trailing/explicit-cold peer readings and negative local/tolerance controls. SC-RD07: preserve legacy boolean across sequence/tolerance boundaries and spaced/invalid JSON parser differences. SC-RD08: source-composed and canonical generated production sampler/render/handler parity; focused existing node/gauge compatibility if composed locally.

All HTTP fixtures are disposable local synthetic sequence responses. They measure code paths, not a real multi-member cluster, book convergence, partition, retained recovery or financial behavior.
