## Restart versus intentional fresh start

| Transition | Required identity and recovery | Current gap / bounded delivery |
|---|---|---|
| Consumer process restart, retained inbox and ledger | Reuse epoch, bundle/job IDs and prior attempts; verify retained hashes | Existing coordinator recovery reused; receipt-directory binding implemented and tested before publication. |
| Member process restart with /data retained | Same CLUSTER_EPOCH and ID format; snapshot plus log tail continues counters | Source supports counter restore; epoch/storage binding remains unimplemented. No distributed live recovery claim. |
| Member replacement with emptyDir lost | Recover authoritative state before admission; keep epoch only for genuine continuation | Never classify an empty member as a new trading run merely from container ID. Full HA proof remains open. |
| Intentional empty engine, retained SQL | New platform epoch plus reviewed projection namespace/migration; preserve history | Unsafe today: bare trade keys collide, positions combine epochs, order filters lack epoch. Do not deploy fresh engine into old projection on strength of this receipt fix. |
| Intentional new receipt stream | New independently provisioned receipt directory, explicitly supplied new epoch; retain old directory/inbox/ledger | New scope binding permits identical local counters in distinct directories; old directory rejects new epoch. Does not authenticate the first supplied identity. |
| Late/duplicate receipt | Original directory and epoch; exact cut/hash validation; duplicate bundle dedup | Wrong epoch rejected before publication; identical valid input reuses bundle/job. Late results cannot replace a different epoch's result. |
| Crash during binding/publication | Commit scope first, publish second; retry same epoch only | SQLite transaction rollback before commit; retained binding after commit, even if no bundle published. No automatic rebinding or deletion. |
| Corrupt/missing lineage store | Fail on corrupt store; missing store cannot prove prior custody | New inbox is a new custody domain. Backup scope DB with inbox; deleting/moving it loses the guard. No global authority claimed. |

## Proposed interfaces and path ownership

Bounded implementation: YU18 `eod-risk-bundles/receipt_scope.py`, `bridge.py`, `tests/test_recovery_identity.py`; component docs and RI-06 task/index. No deterministic-core, wire schema, SQL migration, UI or demo edits. Existing bridge CLI/call arguments remain compatible. A private inbox `.receipt-scopes.sqlite3` records canonical receipt-directory -> clusterEpoch before publishing. First validated import adopts the caller's explicit identity; subsequent calls must agree. Invalid inputs do not reserve a scope. Concurrent first writers are serialized by SQLite. Producer directories stay read-only.

Migration: existing receipts and bundles remain byte-compatible. Before first import with this version, the operator must verify the supplied epoch against the original recorded run; legacy receipts cannot establish it themselves. Existing inbox bundles lack source-directory provenance, so automatic historical backfill is impossible. Do not delete or move the scope DB independently of custody. Separate inboxes or copied directories are outside this guard; signed/platform-issued receipt identity is future work. Same-date valuation-time policy is unchanged.

Broader proposal, NOT implemented: platform-owned immutable run descriptor {epoch, eventIdScheme, recovery lineage} tied to retained engine storage and propagated into producer receipts; require matching descriptors before publishing/admission. Fresh-epoch transition must quiesce, record old common boundary, archive old projection, provision a new scope, validate all members/producers, then enable admission. Never generate identity on consumer restart. Review explicit legacy trade-ID versus epoch-qualified scheme migration before changing publisher/recon keys, or retained replay could double-book old trades. Add epoch-scoped projection keys/queries and reject stale events; retain historical views. Missing/in-flight records must be distinguishable from reconciled records at a common boundary. RI-07 consumer work can depend only on currently supplied explicit bundle clusterEpoch; no new backend engine endpoint is delivered here.

## Trade-ID migration proposal — review required, not implemented

The minimal failing-before fixture is [TradeEpochCollisionTest.java](../../specs/YU18-risk-integration/components/recovery-identity/proofs/TradeEpochCollisionTest.java). It uses actual TradeService and Spring Data JPA repositories over disposable H2 SQL. The old trade is committed before reconstructing the service. The new event has `id=1-B`, `sourceOrderId=fresh-1`; the service returns `sourceOrderId=old-1` and leaves quantity at 100. Desired-safety assertion fails. Same-epoch duplicate and distinct-counter controls pass. The paired [wire fixture](../../specs/YU18-risk-integration/components/recovery-identity/proofs/TradeEpochWireTest.java) calls the real inherited publisher encoder: old/fresh epoch both emit `1-B`, while sourceOrderId changes. This establishes a local wire-to-booking defect; it does not claim MariaDB deployment or distributed recovery evidence.

Proposed staged migration:

1. **Inventory and freeze identity per retained log/projection.** Introduce an explicit immutable eventIdScheme (`legacy-v0` or `epoch-v1`) in the future platform run descriptor, bound to epoch, storage lineage and projection scope. Existing retained epochs stay `legacy-v0` for all original/replayed/late events. A process restart cannot select a new scheme. Unknown/mixed legacy lineage requires operator review; do not infer it from container IDs, timestamps or the current environment.
2. **Add readers and verification before writers.** TradeService single/batch ingestion, TradeRepository, settlement/TCA/regulatory consumers, reconciliation and API/UI consumers must accept both reviewed formats as opaque IDs. Duplicate keys are idempotent only when immutable economics and provenance agree; a conflict must report an error and leave SQL untouched rather than silently returning an unrelated trade. Existing JPA string columns need no widening if the proposed epoch-v1 form is `e1-{epoch}-{tradeSeq}-{B|S}`, epoch restricted to 1..25 ASCII alphanumeric/underscore characters, positive signed-long decimal sequence. Its worst case is 50 characters. Validate every consumer/DDL limit before accepting that format. This is a proposed new-scheme bound, not a new restriction on retained legacy input.
3. **Keep replay keys stable.** Do not rewrite legacy IDs in place and do not emit v1 IDs while replaying a legacy log: that would book already-applied trades again. Persist scheme with the log/epoch descriptor and enforce it on every member/publisher/recon reader before admission. If historical translation is needed, use an audited immutable mapping keyed by original epoch + old ID, with reconciliation at a frozen boundary. Ambiguous unscoped legacy history must remain flagged, never guessed or automatically merged.
4. **Only a reviewed intentional fresh-epoch transition writes v1.** Stop admission, capture original epoch/sequence/checkpoints and unmatched/in-flight population; preserve old SQL and authoritative archive. Provision a new platform scope; require matching descriptor on all members/producers/consumers. Epoch-qualified trade IDs are necessary but insufficient: positions must also be scoped by epoch/account/security, orders/history queries by original epoch, and consumer checkpoints/dedup by matching scope. A separate new projection database can be an explicit transitional design, but must preserve historical access and cannot be selected silently. User-facing historical views belong to RI-07 coordination.
5. **Update all identity producers together.** YU18 should deliberately override inherited YU12 TradeNatsPublisher, YU17 ClusterRecon and any external/capture emitters that construct trade IDs; order source lineage must use the same epoch fallback/descriptor. The current trade fallback 0 and order fallback 1 must not be allowed for v1. TradeService batch and single paths, recon expected IDs, settlement/TCA/regulatory foreign references, read APIs and UI joins must agree. Inventory exact paths before implementation. Do not edit ancestor behavior or propagate broadly.
6. **Receipt and risk lineage.** Future producer receipts must carry the platform epoch/descriptor and exporter namespace, not rely exclusively on first importer assertion. Reconciliation requires matching epoch and common cut sequence/version/hash with complete nonempty witness population (or explicitly proven empty state). Numeric contract IDs remain meaningful only with their bundle/epoch. Risk job/result identity and historical selection already carry epoch; preserve those immutable identities. Missing/late records must be classified as pending, conflicting or missing, not hidden by a new active filter.
7. **Acceptance before activation.** Retained-log restart and snapshot-plus-tail must preserve IDs/counters/scheme. Old duplicate/late events remain exactly-once in their old projection; same local counter in v1 fresh epoch is a distinct row, never an old duplicate. Reject cross-epoch joins and wrong-scheme replay. Exercise crash at each transition checkpoint; before admission, recovery must resume the same recorded stage or fail closed. Prove position separation, not just distinct trade-row count. Include actual disposable MariaDB plus consensus recovery; current H2 proof is a defect witness, not that acceptance.

No production key/schema change is included. Coordinator review and an explicit scoped migration assignment are the next action; RI-06 is partial while this blocker remains.
