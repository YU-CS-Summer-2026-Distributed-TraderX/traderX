## Open problems, in priority order

### P1 — Cross-epoch history transfer (the design gap; everything else is secondary)

**Terminal evidence:** `cannot bootstrap at business boundary 159: local history ends at business
seq 39 (node fell behind) — snapshot transfer needed`.

Mechanism: every promotion/re-election claims a new epoch; the new epoch's recording starts at the
then-current watermark. A follower that faults/restarts across an epoch flap needs sequences that
exist only in a PRIOR epoch's recording (40–158 above). `AeronArchiveReplayMerge` replays exactly
one recording. So any follower not caught-up-at-the-boundary is unjoinable, honestly fail-closed.

Your original spec contract (recap §"Recommended resumption point") is the fix shape:
1. Promoted primary exposes a checksummed snapshot/journal bundle with an exact
   `(leaderEpoch, inputSeq, recordingPosition, dataSessionId)` boundary — the SBE
   `SnapshotManifestMessage` (id=6) and `ReplayRequestMessage` (id=5) you stubbed are still unused
   and fit this.
2. Install on an uncheckpointed/epoch-mismatched follower whose journal cannot prove S0−1 (the
   journal-cut bootstrap already handles the can-prove case — keep it as the fast path).
3. Alternative worth costing: **replay-chaining** — walk recordings oldest→newest across epochs
   (each epoch's recording covers [startSeq..next epoch's startSeq)), replaying each in sequence
   before merging live. No new wire protocol, but needs per-recording boundary discovery (the
   probe generalizes: first fragment of each recording gives its startSeq) and careful handling of
   the gap between one epoch's recorded tail and the next epoch's start (fragments published while
   NO archive destination was connected are in no recording — with `1e59c31` that window is now
   only the awaitConnected startup race, but it is not provably zero).
4. The journal-cut bootstrap plus a bundle/chain must compose: cut to S0−1 when provable, install
   the bundle only otherwise.

### P2 — Election flap rate under load (epoch-churn driver)

Under kind host load, Lease elections flap every few minutes; each flap bumps the epoch and moves
the boundary. This is why the caught-up-pair scenario never stays staged long enough to crash-test.
The YU02 lease tuning (renewal/duration), fast-witness enablement on kind (it appears disabled —
the crash test's promotion took >10s via the heartbeat path against a 3s gate), and the graceful
Lease release on shutdown (`LeaderElection.stop()` never releases — YU02-owner fix, still open)
all reduce churn. Fixing P2 makes P1 rarer but not unnecessary.

### P3 — Static DNS resolution (partially mitigated)

Aeron resolves endpoint DNS once at publication creation. Fixed for the primary data path
(`1e59c31` + retry). Still unfixed: a CONTROL-side wedge where one side's control publication
points at a dead IP while the other side waits (observed: pair wedged asymmetrically until the
stale side restarted). The control agent needs re-resolution/re-init on peer-IP change (watch the
pod IP via the k8s API, or recreate the control publication when `peerStale()` persists past a
threshold while the Lease holder looks alive).

### P4 — Environmental (kind harness)

- **local-path PV vs required anti-affinity:** the provisioner binds the PVC on the occupied node;
  the pod wedges Pending. Heal: delete PVC+pod, re-provision. The cycle script self-heals this;
  fold it into `scripts/yu11/start-aeron-ha-kind.sh`.
- **PVC deletion race:** deletion can re-bind if the StatefulSet recreates pods before
  finalization — a resurrected journal splits the pair's origins (observed: primary at lineage
  4888, fresh follower expecting 0). Always `kubectl wait --for=delete pvc/...` before rescaling.
- **Launcher rollout window:** 10m `rollout status` is routinely eaten by the PV heal + slow
  boots; the launcher aborts before testing. Decouple bring-up from verification.

### P5 — Crash-test gate calibration

The 3000ms promotion gate assumes the fast-witness path (30–60ms design target). On kind the
promotion went via heartbeat-stale detection in >10s. Either enable fast-witness in the kind
profile or gate on the Lease-path budget. (The 9,502ms graceful-deletion measurement from your
session is a separate, known number — this is about force-delete.)

## Approaches tried and rejected (don't re-walk)

- **Probe on the shared replay endpoint** — driver-side endpoint residue starves the merge
  subscription (`image=null` despite 20s+ gaps). Dedicated port is required.
- **Bootstrap on the demotion path** — unsound twice over (live Journaler races the cut; state
  can't rewind). Boot-path only.
- **Fresh-journal probe** — pointless: a fresh journal can only ever join at the origin; either
  the origin contract succeeds or FAULT_GAP is the correct outcome. Skipping it also removes the
  port hazard for the common case.
- **`resetTo`-style ring-cursor alignment** — Disruptor 4.0.0 removed it; the lineage base offset
  (business = base + ringSeq) achieves the same without touching ring internals.
- **Heartbeat schema extension for the epoch boundary** — rejected in favor of probing the
  recording itself: no schema/golden-vector churn, and the recording is the authority ReplayMerge
  actually joins.
