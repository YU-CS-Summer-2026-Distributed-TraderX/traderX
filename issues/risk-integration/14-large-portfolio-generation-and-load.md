# RI-14 — Synthetic portfolio generation and risk-engine scale testing

Updated: 2026-10-07. Status: in progress: seeded generator/local driver integrated at a0d6da0b; massive load, broader coverage and tool comparison remain. Maintainer: coordinator; original delivery notes below retain their dates.

## Two different scales

Test both one large portfolio and many independent portfolios. Vary trades per portfolio, portfolio count, instrument mix, maturity/currency concentration, scenario count, time grid, Greeks method, precision and cold/warm compilation. Trade count alone does not measure work. Never split a portfolio's nonlinear exposure/VaR/ES into jobs and sum the resulting risk numbers.

## Generator

Use a seeded Python CLI to build schema-valid, deterministic synthetic inputs. Reuse engine schemas/examples without copying its pricing logic. Define unique portfolio/trade/submission identities, valuation dates, consistent schedules, long/short signs, curves/FX and explicit synthetic provenance. Keep source and small fixtures tracked; large corpora and derived outputs outside the public checkout.

Start with accepted USD Treasury bills/notes. Expand only to supported swaps/swaptions and conventions, with complete fixing data where needed. Unsupported instruments/currencies are named negative cases, not silently substituted. Mixed-currency market-risk aggregation is held until the October 7 audit defect is corrected.

Proposed size ladder, subject to memory estimates: 100, 1,000, 10,000, 100,000 trades; larger only after measuring. Add both repeated shapes for warm-cache capacity and heterogeneous shapes for compilation stress. Estimate cube memory as paths × dates × trades × stored bytes plus intermediates, retained outputs and serialization. Streaming/bounded generation must not overwhelm the load host.

Produce a manifest containing seed, schema/engine revision, counts, checksum, expected supported/refused coverage and economics aggregates. Independent small golden cases verify correctness; a large run completing is not financial validation.

## Drivers and acceptance

- Preferred: Python corpus generator plus k6 HTTP load driver using pre-generated inputs, submission/poll workflow, checks and arrival-rate scenarios. Account for SharedArray access/JSON copying and large-payload memory; prove generator throughput independently.
- Alternative: an async Python client for streaming huge request bodies and detailed numerical checks. Locust is an option when a Python-native distributed HTTP-user harness is useful; select after a small tool comparison, not by familiarity alone.
- Keep engine-only compute benchmarking separate from API load and TraderX trade-to-export-to-risk tests. Direct synthetic portfolios measure engine scale; an end-to-end subset proves TraderX provenance and mappings without hand-entered economics.
- Report submission latency, queue wait, compute/serialization/total completion time, completed portfolios and trades per second, polling pressure, result bytes, memory/device utilization and compile counts. An HTTP202 is acceptance, not completed pricing.
- Include overload/backpressure, restart/interruption, lost replies, duplicate requests and corrupted/incomplete inputs. Never auto-resubmit an uncertain job without the agreed identity contract.
- Reproducible local smoke first; CPU/GPU/device scaling and massive concurrent portfolio campaign wait for credits. Report one host/device versus multi-host scope explicitly.
