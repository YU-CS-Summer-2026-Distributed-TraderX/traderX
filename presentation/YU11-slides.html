The gap YU10 left

The engine was fast; its replication was the tax

  • HA cost most of the throughput. The warm-standby leg replicated every input over File-backed NATS at ~10.6k events/s — so the HA deployment booked far fewer orders than a single BLP. Safety was paid for in throughput.
  • An ACK meant "queued," not "durable." The path could acknowledge replication that was still only in memory on the follower — not yet forced to its journal.
  • Failover sat on the Kubernetes control plane. Lease renewal + pod-termination observation set the floor, and a wiped replacement had no proven way back after a leader change — effectively one-shot failover.
The matching core was never the bottleneck (~6M ops/s). The replication transport was — in both its throughput and its recovery story.

THE MECHANISM · AERON + SBE, ZERO-COPY

One sidecar, one publication, a fixed 64-byte message

An Archiving Media Driver runs as a sidecar in each order-matcher pod. Each input event is encoded into a fixed 64-byte SBE message written directly inside the tryClaim buffer — no intermediate copy. A single manual-MDC publication fans the same fragment to the local Archive and the peer follower, so both share one session and one position.

input event → SBE encode in tryClaim (64B) → one MDC publication → { local Archive · peer follower }
— one session · one position · one fragment boundary —
follower: journal the fragment → durable ACK (never before journaledSeq advances)
Aeron replaces only the replication data/ACK leg — one flag (BLP_REPLICATION_TRANSPORT=nats|aeron) with NATS-authoritative shadow comparison and one-value rollback. Matching, risk, journal, and CQRS are untouched.

CORRECTNESS · CROSS-EPOCH RECOVERY

A wiped replacement rejoins — and can promote on the next failure

The hard part of hand-built HA isn't the happy path — it's a replacement member with an empty disk joining a cluster whose leader has already moved to a new epoch. YU11 proves it end to end.

THE CONTRACT

Snapshot bundle, bound to an exact boundary

A promoted primary exposes a checksummed snapshot + journal bundle stamped with its exact (epoch, inputSeq, Archive position, session). The joiner installs it crash-safely, replays zero local tail, merges into the live recording, and reaches Ready with matching order/read-model hashes on both nodes.

PROVEN LIVE

Empty PVC → rejoin → 2nd failover

Empty PVC → bundle at marker 10492 / Archive pos 77568 → snapshot(@64) loaded → 2/2 Ready. The original primary was force-deleted; the bundle-recovered follower promoted at epoch 5 and a fresh replacement rejoined. The "one-shot failover" gap is closed.

Getting here was an honest journey: a split-publication dead-end (8 compensating fixes), the MDC pivot that made one publication carry one shared stream, then lineage-continuous sequencing — business sequence numbered across the leader lineage, not the ring — so a cut journal can prove continuity across an epoch change.

HONEST FINDING · A LATENT BUG, EXPOSED

An ID generator living outside replicated state reused an order ID

Zero-tail bundle install removed the paths that had masked a latent bug — and exposed it cleanly: 12 orders warm, nextRef 8; after the second crash, the promoted follower reissued ord-013-0008.

  • Root cause. The monotonic nextOrderRef counter lived outside the deterministic replicated state. Journal replay and follower injection both apply ORDER_NEW without advancing it → a later snapshot holds newer orders but a stale counter → the promoted node reissues an ID it already used.
  • The fix is structural. Every future-output generator must be part of the replicated, snapshotted state, and recovery must assert it exceeds every ID ever issued — not merely every ID still retained in memory.
The principle YU11 pins down: snapshot completeness covers counters, ID generators, idempotency, risk reservations, symbol identity, and control versions — not just the visible book.
