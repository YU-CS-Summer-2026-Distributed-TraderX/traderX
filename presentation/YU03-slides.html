The problem

YU02 had zero pre-trade risk control

The matcher's only "limit" was the order's own limit price. No credit, buying-power, exposure, restriction, or kill-switch checks — an order with a valid ticker simply matched and filled. That's not a system a broker or exchange can run.

Control baseline: SEC Rule 15c3-5 (Market Access) — pre-set credit & capital limits, erroneous-order checks, restrictions, and a kill switch, enforced before an order reaches the market.

DESIGN · TWO TIERS

Fast screening, then an authoritative decision

In-memory admission gateway

preliminary · no DB/REST per order

Holds event-fed local replicas of account status, entitlements, restrictions, risk limits, kill switch, and price freshness. Fails closed on staleness or version gaps.

The BLP decides authoritatively

deterministic · in sequence order

The single-writer engine re-checks and reserves exact exposure in global sequence order before an order is executable. That determinism is why it belongs in the BLP — rejects replay identically from the journal.

CONTROL PLANE · LIVE

Operators steer risk in real time

  • Restrict a security or flip the kill switch live — demonstrated engage → orders rejected → disengage → orders flow again, in seconds.
  • Versioned & sequenced. Every control change is a numbered event applied on the single-writer BLP — no racy in-place mutation.
  • Restricting cancels resting orders through explicit sequenced CANCEL events (FR-IMRG24) — never a silent book change.
  • Authenticated — control calls carry an operator identity + a risk-control token.

HOW IT REACHES THE ENGINE

A control change is an event, not a mutation

Every control does two things: it updates the edge replica, and it sequences a versioned control event onto the same input ring as orders. The single-writer BLP applies it to its authoritative risk state in global order — so a control and the orders around it can't race, and the whole decision is journaled and replayable.

// RiskControlController — operator POST /risk/control/account
replicas.applyAccount(id, enabled);             // tier 1: edge replica (pre-screen)
engine.submitAccountControl(id, enabled, version);  // tier 2: event onto the BLP input ring

// MatchingEngine — the single BLP thread, in sequence with orders
case TYPE_ACCOUNT_CONTROL     -> onAccountControl(e);      // → authoritative BlpRiskState
case TYPE_RESTRICTION_CONTROL -> onRestrictionControl(e);  // + sequenced CANCELs (FR-IMRG24)

DETERMINISM · AUDIT

Authoritative decisions are sequenced & replayable

  • Every authoritative BLP decision is on the journaled ring — accept-and-reserve, or reject — alongside every control & reservation event. None enter the book or emit a market-facing event on reject.
  • Deterministic in sequence order — the same event stream reconstructs the same accept/reject decisions, every replay.
  • Cheap edge rejects are not journaled — the gateway refuses obviously-bad traffic at the HTTP edge, before the ring (that's the point of tier 1). The audit record is the authoritative risk decisions, not every malformed 422.
  • That's the SEC 15c3-5 audit story: a replayable record of every risk-limit reservation and authoritative rejection — what was blocked and why.
