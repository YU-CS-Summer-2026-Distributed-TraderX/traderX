The problem

Correct isn't the same as operable

  • Credentials lived in committed manifests. A repo checkout exposed working DB and JWT secrets.
  • The journal grew without bound. One ever-growing file on the pod's PVC — eventual disk exhaustion, and nothing off-box if the volume was lost.
  • A stale jar could deploy silently. A Docker layer-cache hit on COPY build/libs/*.jar could bake yesterday's bytecode into a "new" image.
  • No runbook. A real node/zone/DB incident had no documented recovery path.
These aren't correctness bugs — they're the operational sharp edges that turn a working system into a 3am page. YU09 closes four of them.

HARDENING 1 · CREDENTIALS, FAIL-CLOSED

No credential lives in git

DB and JWT/dev-token credentials move out of manifests into Kubernetes Secrets via secretKeyRef (FR-OH01–04). The Secrets are required — a missing one is a visible CreateContainerConfigError, never a silent fall back to a dev default (NFR-OH04).

HARDENING 2 · BOUNDED + DURABLE JOURNAL

The journal rotates and survives

At every snapshot boundary the active journal is closed off as an immutable segment and a fresh file takes over — bounding local disk — then each segment uploads to GCS via HMAC, off-box (FR-OH20/21). Fail-safe: a segment that fails to upload is never deleted (FR-OH23); the upload runs off the journaler thread (NFR-OH02); off by default, zero throughput cost (NFR-OH01).

// live: forced a 20s snapshot boundary, archival enabled

HARDENING 3 · DEPLOY SAFETY

Never ship a stale jar

The publish pipeline now runs gradlew --no-daemon clean bootJar before every docker build, for every JVM build context (FR-OH30). A Docker cache hit on the jar copy can no longer bake stale bytecode into a "new" image — the jar is always freshly compiled first.

// publish-generated-state-branch.sh — ordering is the whole point
L2336  ./gradlew --no-daemon clean bootJar   (fresh jar)
L2340  docker build -t $image …              ← always after the rebuild ✔
       guarded to contexts with a build.gradle · pinned by a regression check
A build reproducibility guarantee: what deploys is always what the current source compiles to, not whatever jar happened to be on disk.

HARDENING 4 · INCIDENT READINESS

A runbook for the real topology

A written DR runbook covers the failure modes the cluster can actually suffer — scoped honestly to how it's actually deployed (single-zone GKE, single-replica MariaDB), not an idealized HA diagram (FR-OH40).

Pod
order-matcher / BLP loss — reschedule + journal replay
Node
blp-pool / default-pool loss — blast radius + recovery
Zone
single-zone reality — what's lost, how to restore
Data
MariaDB loss — projection is a rebuildable read-model
Each mode documents blast radius, recovery procedure, and the observed RPO/RTO — an honest account of a single-zone deployment, not a promise the topology can't keep.
