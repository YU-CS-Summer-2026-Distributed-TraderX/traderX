The problem

A database call on every order is a wall

The traditional matcher did a synchronous DB round-trip per order — the throughput ceiling and the latency floor. YU02 replaces that path with the LMAX Disruptor architecture: match in memory, persist asynchronously.

Why YU02 exists02
FEATURE 01 · THE CORE

A single-threaded, event-sourced matching engine

  • One thread, no locks. Orders are sequenced onto a Disruptor ring buffer; the engine matches on a single thread — deterministic, contention-free.
  • In-memory book. No synchronous DB call on the hot path; the match happens at memory speed.
  • CQRS. MariaDB becomes an async read-model projection, not the source of truth — the event journal is.
  • Deterministic replay. The same event stream always rebuilds the same state — the foundation for recovery and HA.
The BLP core03
FEATURE 02 · DURABILITY

Journal + snapshot — fast recovery, no data loss

  • Every input event is journaled to disk before the engine acts on it.
  • Periodic snapshots checkpoint in-memory state at a consistent boundary.
  • On restart, replay the journal from the last snapshot forward — recovery in seconds, not a cold rebuild.
  • Readiness-gated: the pod refuses traffic until replay completes, so no half-recovered engine ever serves an order.

FEATURE 03 · KUBERNETES

Two runtime modes on GKE

Single-BLP

1 replica · max throughput

One engine, no replication overhead. The fastest path — used when throughput matters more than instant failover.

HA StatefulSet

2 replicas · failover

Leader election (Kubernetes Lease) + NATS JetStream warm-standby replication. Pod-GET fast failover promotes the standby in ~2–3s on real pod death.

FEATURE 04 · CI/CD

GitOps deploys with a human approval gate

  • Cloud Build → Cloud Deploy. A git push automatically builds, tests, and pushes a uniquely-tagged image.
  • Nothing touches the live cluster until a human approves the release — the gate is enforced, not advisory.
  • Git is the source of truth — closes the drift class of bug where prod runs an image older than the committed fix.

RESILIENCE · HA FAILOVER

How the standby takes over

  • Leader election (Kubernetes Lease). The two BLP replicas compete for a k8s Lease; the holder is PRIMARY and renews it, the other is a hot STANDBY watching the lease.
  • Warm-standby replication (NATS JetStream). The primary streams every input event to a durable JetStream stream; the standby replays them continuously, so its in-memory book stays identical — no cold rebuild on takeover.
  • Pod-GET fast failover. Rather than wait a full lease TTL, the standby checks the primary pod directly — on real pod death it promotes in ~2–3s.
  • No split-brain. Admission is fenced: a replica that isn't provably the leader refuses orders (fail-closed), so at most one engine ever serves.
