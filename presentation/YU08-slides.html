A large order is no longer one market-moving print. YU08 adds a parent-order execution layer — TWAP and VWAP algorithms that slice an order over time and drip child orders into the book, through the exact same risk-checked path as a manual order.

The problem

One big order moves the book against you

  • Only one execution primitive. Every order — 100 shares or 100,000 — hit the book as a single print. A large one walks the book and signals intent.
  • No scheduling, no participation strategy. No way to spread a parent order across time, or to size slices by when the market actually trades.
  • YU07's data sat unused. We built a real tick store (live + NYSE TAQ) — but nothing consumed it to make execution decisions.
A sell-side OMS needs execution algorithms as table stakes. YU08 is the first component that both schedules execution and consumes the historical market data YU07 produced.

THE COMPONENT · INDEPENDENT SERVICE ON :18120

Two algorithms, one scheduler

TWAP — time-weighted

equal slices across the duration

Splits the parent quantity into equal buckets over the requested window; the integer-division remainder folds into the last bucket. A bucket is submitted as its start time comes due (FR-AE02).

VWAP — volume-weighted

slices follow a volume profile

Sizes buckets by a volume profile — heavier when the market trades more (open/close). The profile comes from a pluggable source: a synthetic U-curve, or YU07's real tick store (FR-AE03).

Runs as its own Spring Boot service and its own Deployment — no change to the order-matcher BLP: no new Disruptor rings, journal, or matching code (NFR-AE01/04).

THE KEY IDEA · NO PRIVILEGED LANE

Every child is just an order

Each child order is submitted to order-matcher's same POST /orders as a hand-entered order — same risk gateway (YU03's SEC 15c3-5 checks), same BLP. Algorithmic flow is risk-checked identically; there is no bypass (FR-AE04, NFR-AE02).

THE PAYOFF · YU07 DATA, PUT TO WORK

VWAP slices by real volume

VWAP bucket sizes are not a flat split — they follow the volume profile. The duckdb source queries YU07's tick store for the symbol's trades; any security with no history falls back to the synthetic curve, so it never blocks (FR-AE09).

// live: same 600-share IBM order, two algos
TWAP (flat)      [100, 100, 100, 100, 100, 100]   sum=600
VWAP (profile)   [136,  92,  70,  70,  92, 140]   sum=600   ← U-shaped ✔

Live proof · durable resume

It owns its own recovery

Every parent-order transition is appended to the engine's own JetStream stream before it touches memory. On restart it replays that stream — same event-sourced discipline as the BLP, one layer up (FR-AE07/08, NFR-AE03).

// live: 500-share TWAP, 6 buckets — kill the pod mid-run
BEFORE KILL    submitted=3/6  children=[…0059, …0060, …0061]
✗ kubectl delete pod   → Kubernetes reschedules → replayed 116 events
AFTER RESTART  submitted=3/6  children kept ✔  (rebuilt, not re-created)
FINAL          COMPLETED 6/6  6 unique children  — no bucket re-submitted ✔
No operator intervention, no synchronous fetch to another service, no double-submission on replay — the schedule and observed fills survive a crash.
