The front office matches, screens, and controls risk. YU05 is the back office — settlement, reconciliation, regulatory reporting, TCA, and real auth — built on one idea: because the journal is the source of truth, every compliance obligation is a deterministic projection of it.

The problem

A fast, safe matcher still isn't a broker's system

  • Trades booked and forgotten — marked settled the instant they booked; no real T+N lifecycle.
  • A read model you had to trust — the async MariaDB projection could silently drift from the authoritative journal, with no way to prove it hadn't.
  • No reproducible audit trail — a regulator query answered from a mutable projection isn't defensible.
  • A shared-token stopgap — every service trusted one secret; no real identity or per-account entitlement.
These are the back-office & compliance pillars a sell-side OMS lives or dies on — settlement, recon, regulatory reporting, best-execution (TCA), and access control.
Why YU05 exists02
THE SPINE · JOURNAL = SOURCE OF TRUTH

Every obligation is a projection of the journal

One executed fill — symbol, price, qty, side, account, timestamp, deterministic trade id — sourced from the order-matcher journal. Settlement, reconciliation, regulatory export, and TCA are all views over that record, plus the auth layer that makes exposing it safe.

Strictly downstream of the BLP. None of it sits on the order-admission path; none mutates journal or BLP state (NFR-PTC09). Settlement/recon write only their own MariaDB rows; full-history and regulatory exports are read-only shadow replays. Same discipline as every state: new capability, hot-path determinism untouched.
Event sourcing pays off downstream03
Capability 1 · settlement lifecycle

A trade now has a life: Processing → Settled

A booked trade starts Processing with a computed T+N settlement date (default T+1 business day) and advances to Settled on a scheduled sweep — or a manual operator force.

# live on kind — books a crossing pair, then force-settles the new trade
$ bash yu05-settlement.sh

  · books a crossing IBM pair        → one fill → one trade row
  · reads it: state=Processing, settlementDate = T+1
  · POST /trades/{id}/settlement/force   (operator override, admin JWT)
  · re-reads: state=Settled
T+N = trade date plus N business days — when cash and securities actually change hands. Equities settle T+1 (next business day) under the current US standard; the delay is the window we model as Processing.

CAPABILITY 2 · THE CQRS INTEGRITY CHECK

Proving the read model hasn't drifted

A scheduled sweep runs every 10s, paging new journal blotter entries forward from a cursor and classifying each against its MariaDB row. GET /recon/status just reads the latest running totals — it doesn't recompute on request.

// ReconciliationService — runs every 10s, forward-only via a cursor
@Scheduled(fixedDelayString = "${recon.poll.interval-ms:10000}")
void sweep(){ for (e : blotterSince(cursor)) classify(e); }
//  not in DB → MISSING_IN_PROJECTION · fields differ → FIELD_MISMATCH · else MATCHED
// on-demand full-history orphan sweep (admin) — the reverse case, live:
local=11   journal-backed=7   orphan_in_projection=4
→ TRADE-22214-AABBCC, -DDEEFF, -GGHHII, TRADE-52355-AABBCC   (DB-seed rows,
                                                              no journal fill behind them)
Those 4 orphans are the manually-seeded DB trades — no journal event backs them, so the sweep flags them. Recon catches drift in both directions, by construction.

CAPABILITY 3 · REPRODUCIBLE AUDIT

Answer a regulator from the source of truth

The regulatory export replays every lifecycle event (accept, reject, partial, fill, cancel, book) in an input-sequence range — sourced from the journal, never the projection — and is a pure function of (range, seed). No wall-clock, no live query.

// GET /regulatory/report?fromSeq=0&toSeq=1000000 — called twice, live
call 1     records=16     sha=c5a81b094d08eff5
call 2     records=16     sha=c5a81b094d08eff5
→ byte-identical across calls ✔   (reproducible from the journal, not the projection)
range = the [fromSeq, toSeq] journal window to report. seed = the fixed initial book the replay starts from — the same starting condition the live engine booted with. Each call spins up a fresh shadow engine, seeds it, and replays the journal: same journal + same seed → identical records, every time.

Capability 4 · transaction-cost analysis

Execution quality, off the hot path

Per-trade TCA (transaction-cost analysis) — arrival price, a TWAP benchmark, and signed slippage-in-bps — computed entirely read-side in trade-processor against a price-history store fed by the existing tick feed. No new data source, no BLP involvement.

TWAP = time-weighted average price — the benchmark the fill is compared against. bps = basis points (1 bps = 0.01%). Convention: positive = worse than benchmark, negative = better. So −102.3 bps is price improvement — this Sell filled ~1.02% above TWAP.

TCA computes wherever the security has captured price history; a symbol with no ticks in range returns a null benchmark rather than a guess — honest by construction.

CAPABILITY 5 · REAL AUTH & ENTITLEMENTS

Real identity, per-account entitlement

Every endpoint now requires an HS256-verified JWT (JDK crypto only), replacing the shared-token stopgap. Two entitlement axes, both enforced live:

Cross-account = an endpoint returning data spanning many accounts (e.g. the firm-wide regulatory report), so it needs an admin claim; an account-scoped token may only touch its own account's data.
