Speaker notes · slide 1

Yes — this is still our BLP matching engine. "BLP" is the Business Logic Processor: the same deterministic, single-threaded matching + risk core we've carried since the early states. YU12 does not rewrite it — the engine runs unchanged. What changed is how it's fed (everything now arrives through the consensus log) and how it's replicated (three copies kept identical by Raft).

The one-line story: YU11 gave us correct high-availability, but built it by hand — lease election, a witness tiebreaker, snapshot-bundle transfer. YU12 throws that machinery away and lets Aeron's Raft consensus provide election, log replication, and wiped-member recovery as built-in primitives.

The gap YU11 left

Correct HA — but hand-built, brick by brick

  • A tower of bespoke machinery. Lease election, a fast-witness CAS tiebreaker, checksummed snapshot-bundle transfer, journal-cut bootstrap, lineage-continuous sequencing — every one hand-written, and every one a place an adversarial-timing bug can hide.
  • Fencing was a proof you had to keep holding. "A partition minority must not admit orders" was maintained by witness logic — not a structural guarantee.
  • Failover still on the k8s control plane. Lease renewal + pod-termination observation set a floor of seconds.
  • And it surfaced an ID-reuse bug. A generator living outside the replicated state reissued an order ID after promotion.
The question YU12 answers: what if election, log replication, and empty-disk recovery were consensus primitives instead of code we maintain — and split-brain were structurally impossible rather than fenced?

THE MECHANISM · RAFT CONSENSUS

The BLP matching engine as a replicated state machine

The inherited BLP matching engine (MatchingEngine) runs unchanged as an Aeron Cluster ClusteredService. Three members; Raft majority vote provides leader election, log replication, and commit ordering. Every input — orders, cancels, price ticks, control updates — enters only as a committed consensus-log message, then applies single-threaded through the same engine and two-tier risk.

client → gateway → Raft consensus log (majority commit) → apply (single thread) → BLP matching engine + risk → output
— every member applies the identical committed sequence, in the same order —
Split-brain is structurally impossible: a partition minority can't win a majority vote, so it can't elect a leader, extend the log, or admit an order — no witness, no fencing proof to maintain. A wiped member rejoins by pulling a snapshot and replaying the log: a Cluster primitive, not five hand-built slices.

CORRECTNESS · NO ID REUSE, BY CONSTRUCTION

The bug that took YU11 a diagnosis is gone by design

In YU11 the nextOrderRef generator lived outside the replicated state, so a promoted node could reissue an order ID. In the cluster there is nowhere outside the replicated state for it to live.

  • Every future-output generator is cluster state. orderRef, trade counters, idempotency, risk reservations, symbol identity, control versions — all carried in the log and in onTakeSnapshot, bound to an exact applied log position.
  • Recovery fails closed. On load and on promotion the service asserts every restored generator strictly exceeds every ID ever issued — not merely every ID still retained in memory. A violation refuses readiness.
Proven: zero order-ID reuse across ~80 leader kills and every recovery-matrix case. The no-reuse property is now a structural guarantee, not a test that has to keep passing.

The three numbers — every "X / Y / Z" is three consensus timeouts, in milliseconds

  • X = heartbeat interval — how often the leader sends "I'm alive" pings.
  • Y = heartbeat timeout — how long a follower waits with no ping before it declares the leader dead and starts an election. This is the detection window and the single biggest lever.
  • Z = election timeout — bounds the voting round (the random nomination delay is up to half of Z).

"First tune" = our first step off Aeron's out-of-the-box defaults (200 / 10000 / 1000 — a 10-second timeout, which is why the default failover is ~12 s). "Tune" just means we set these as env values; they change live, no rebuild. So 100/1000/500 → 100/400/200 → shipping 50/200/100 is us tightening the detection and election windows one step at a time. (The shipping config adds a 4th knob too: a 25 ms canvass-status interval.)

What the callout means, plain-English

"system-facing FIRST_APPLY" — we time from the instant we kill the leader to the instant the new leader commits and applies the first order. That's "the cluster is matching orders again," not merely "a leader got elected."

"node-clock-precise" — to keep measurement error out of the number, the test prints a millisecond timestamp and runs kill -9 in the same command on the leader's own machine, so no network or API delay sneaks in. The new leader stamps its own clock when it applies the first order; the machine clocks are NTP-synced, so the gap between the two is the true outage.

"election-stable under a full flood" — we ship the fastest timeout config that never causes a false election under heavy load. Tighter settings hit 275 ms, but during the brief snapshot pause a too-twitchy follower wrongly thinks the leader died and holds a needless election. We ship the tightest config that never does that.

"the FIX/REST gateway survives the leader change" — the gateway holds one long-lived cluster session; when leadership moves, that session follows the new leader automatically, so the trader's connection never drops and their next order just goes through.

HOW · TWO INDEPENDENT DESIGNS, CROSS-CRITIQUED

Chasing sub-second: what actually moved the numbers

CLIENT-FACING · < 500 ms ACHIEVED

Native leader following

The old client tore down its session on an ack stall and burned a 1 s connect timeout on the dead endpoint — a 1.6 s bimodal tail. Aeron Cluster sessions are replicated state: the client now holds one session across the kill, re-points on NewLeaderEvent, never reconnects. 10 / 10 kills sub-500 ms, best 279 ms. The "kind redirect wedge" that forced the old workaround was the /dev/shm bug in disguise — falsified on GKE, the cycling machinery is deletable.

SYSTEM-FACING · PHASE-RESOLVED TUNING

The timeout ladder, soak-gated

Instrumented every Aeron election phase with a live counter watcher, then swept the timeouts one fresh epoch per rung — each rung soak-proven before the next. Raw leader election lands in 161–170 ms, and full failover to the first committed order (FIRST_APPLY) in 275–368 ms — all measured node-clock-precise across the whole ladder.

Placement earned the stability: migrated to one member per c3 node (required anti-affinity, Guaranteed QoS) — variance collapsed to a 3 ms spread. No CPU-quota bump was needed; the newer c3 family had free quota all along.

What this slide is

This is the "HOW we made failover fast" slide, split into the two things that matter differently: how long the trader's connection is disrupted (client-facing) versus how long the cluster itself is without a leader (system-facing).

Left box — client-facing (the big win)

Old behaviour: when the leader died, the client threw away its connection and reconnected from scratch — and often wasted a full second trying the dead node first, giving a jumpy 0.8–1.6 s. The fix: an Aeron Cluster session is replicated data, so the very same session can be handed to the new leader. The client now just receives a "NewLeaderEvent" message and keeps going — no reconnect at all. Result: all 10 test kills recovered in under half a second, best 279 ms. Bonus: the old "wedge" bug that forced the reconnect workaround turned out to be the same /dev/shm bug we'd already fixed elsewhere — so a whole pile of workaround code can be deleted.

Right box — system-facing

We added instrumentation that logs each internal step of an election, then swept the timeout settings rung by rung, proving each one stable before moving on. The pure leader election is very fast — 161–170 ms — and the full "first order actually served" time is 275–368 ms: the election plus the short hop for the client to re-point to the new leader. Every number was measured node-clock-precise.

Bottom line

The consistency came from hardware placement: each of the 3 members now sits on its own dedicated c3 node with guaranteed CPU, which dropped the run-to-run spread to 3 ms. And it cost nothing extra — the c3 machine family had spare quota, so no quota request was needed.

NFR-AC02 · pipelined gateway07

The point of this slide

People worry that adding consensus — three machines agreeing on every single order — will throttle throughput. It doesn't. The cluster was never the bottleneck.

The three bars

Our old NATS-based HA did about 10,100 orders/sec. The number to beat is 25,149/sec — that's a single, non-replicated BLP ("parity," the acceptance bar). YU12 booked up to 135,834/sec.

Two different numbers — don't mix them up

submit/sec = orders accepted into the log per second (we hit 29,000–43,600). booked/sec = trades actually executed per second (up to 135,834). One order can set off a cascade of many trades, which is why booked is the larger number.

Why it's fast, and what the real ceiling is

The engine always had headroom — it replayed a 740,000-event log in seconds. The real bottleneck was the gateway sending orders one at a time and waiting for each confirmation (~1.2 ms each). "Pipelining" means firing a whole batch into the log at once and collecting the confirmations as they stream back; that took a 200-order batch from 250 ms down to 38 ms. So the ceiling is how fast you can push orders in (the gateway), not the matching or the consensus — and we clear the acceptance bar several times over.
