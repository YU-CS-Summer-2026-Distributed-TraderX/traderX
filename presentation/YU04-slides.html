The problem

YU03's control state was a one-shot fetch

The gateway replica learned its account/security universe from a single REST call at startup — and was never updated again while running. An account or security that changed after boot was invisible to it until the next restart; with no versions or watermarks, it couldn't even detect that it was stale. And the startup fetch itself could race changes happening mid-fetch.

For a compliance system that's an audit finding, not a bug: "the account was disabled an hour ago — the gateway never heard." The screening universe must track the source of truth continuously, not once per boot.

DESIGN · TRANSACTIONAL OUTBOX

The feed can never diverge from the source

Publish from the same transaction

account-service · reference-data

Every control change writes the business record and an outbox row in one database transaction. A publisher ships outbox rows to JetStream in strict version order — never skipping a failed row. If the write committed, the feed will carry it.

Two independent durable streams

TRADERX_CONTROL_ACCOUNT · TRADERX_CONTROL_SECURITY

JetStream (not fire-and-forget NATS): retained, replayable, deduplicated by stable message id. A replica that was offline when a delta was published still receives it on reconnect.

DESIGN · WATERMARKED BOOTSTRAP

A replica is ready only when it's caught up

subscribe + buffer live deltas → fetch watermarked snapshot (epoch · version · count · checksum) → verify & install atomically → apply buffered deltas above the watermark, in order → consume live
  • Readiness is gated per source: the gateway admits orders only once every source has caught up to its high watermark — it never screens against a partial universe.
  • No race window: deltas that arrive during the snapshot fetch are buffered and applied after — a change can be missed by neither path.

CONTINUOUSLY LIVE · INTO THE BLP

The feed lands in the engine, in sequence

A source-of-truth change doesn't just refresh the edge replica. The subscriber runs the same two-tier write as the operator control plane — update the replica, then sequence a versioned control event into the BLP's input ring. One sink, two sources: the authoritative engine tracks the live universe in global order, no restart.

FAULT HANDLING · PER-SOURCE

A bad feed quarantines itself — and only itself

  • Every delta carries a source epoch + monotonic version. The replica detects gaps, version regressions, epoch changes, and checksum/count mismatches — corruption can't be silently applied.
  • Quarantine is per source: a fault on the security feed re-bootstraps the security feed; the account feed keeps serving. Readiness is revoked until the quarantined source is clean again.
  • Recovery is automatic: quarantine → fresh snapshot → catch-up → ready. No operator in the loop.
  • Redeliveries dedupe via stable per-version message ids — a republished row is a no-op, not a double-apply.

Design · cost of durability

All of this happens off the hot path

The control feed only changes how the gateway's edge replica is fed. The BLP decision path, the journal and replication wire formats, and the snapshot format are untouched — replica state is rebuilt on every boot, never journaled, so replay determinism is preserved by construction.

Takeaway

Control state joins the event-sourced world

After YU04, no risk-relevant state depends on a pod staying alive. Orders were already journaled and replayable; now the control universe is durable, versioned, and self-healing too — a restarted BLP or a promoted failover replica inherits the exact current risk state, provably.
