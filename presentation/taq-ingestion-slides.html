The problem

The right data, behind the wrong wall

  • Source: a OneDrive / SharePoint share — daily NYSE TAQ quote & trade zips, Feb + Mar 2025, ~650 GB total.
  • Destination: the tick store — gs://…/ticks as Parquet, partitioned by source/date/symbol, so DuckDB can now query the data.
  • The hard part was both transport and storage. The share sat behind an org OAuth policy we couldn't get past, and the files are too big to stage on a laptop.
Two problems, deliberately separated: transport (get raw zips into the cloud, fast) and normalize (TAQ CSV → unified Parquet, disk-free). Each got its own clean solution.

THE SHAPE · TWO STAGES, ONE PREFIX BETWEEN THEM

Land the raw zips, then process them in-cloud

Stage 1 — transport

SharePoint → gs://…/_raw-taq/

Get every raw zip into a GCS staging prefix untouched — no decompression, no conversion. Solved with rclone over WebDAV + a GCE VM (next slide).

Stage 2 — normalize

gs://…/_raw-taq/ → gs://…/ticks/*.parquet

Runs inside the GKE cluster, in-region with the bucket. Streams each zip back out of GCS, decompresses + normalizes in-flight, writes Parquet back to GCS — never leaving the region, never hitting disk.

Landing raw first decouples a one-shot transport from a fast, repeatable, idempotent processing step. Re-run Stage 2 as often as you want without re-touching the source share.

STAGE 1 · THE TRANSPORT BREAKTHROUGH

Beat the OAuth wall with WebDAV session cookies

  • Three dead ends first: rclone's OneDrive OAuth → AADSTS65004 (needs Azure AD admin consent — blocked); CLI hydration → dead (a raw read() never triggers a download, 0.00 CPU); manual Finder clicks → 30 Mbps, one human click per file.
  • The insight: SharePoint libraries speak WebDAV, and rclone can auth with the browser's own FedAuth/rtFa session cookies — no OAuth app, no admin consent (the exact blocker), just an existing sign-in.
# SharePoint doc library over WebDAV, authed with browser session cookies
rclone config create yu-sp webdav \
  url="https://<tenant>-my.sharepoint.com/personal/<user>/Documents" \
  vendor=other headers="Cookie,FedAuth=<v>; rtFa=<v>"

# run it ON a GCE VM in us-east1, 8 parallel streams → datacenter speed
rclone copy yu-sp:NYSE-TAQ-DATA gcs-tick-store:.../_raw-taq --transfers 8
SharePoint throttles per-stream, not per-account, so 8 streams ran at full speed at once. ~1.5 Gbps aggregate moved ~650 GB in ~1–1.5 h, unattended — vs days of manual clicks at 30 Mbps. Cookies minted on the laptop still worked from the datacenter IP.

STAGE 2 · ONE PROCESS, ZERO DISK

Stream → decompress → normalize → write, all in one pipe

gs://…/_raw-taq/taq_quotes_YYYYMMDD_csv.zip │ ▼ gcloud storage cat stream the zip out of GCS (bytes, not a download) │ ▼ funzip decompress the single entry inline, on the fly │ ▼ python3 ingest_taq_quotes.py → DuckDB read_csv('/dev/stdin') → normalize │ ▼ gs://…/ticks/source=taq/dt=…/symbol=…/*.parquet ZSTD, Hive-partitioned
One process, one pipe. The multi-GB decompressed CSV never lands on disk; there's no intermediate Parquet on disk either — DuckDB reads the pipe and writes straight to GCS. Peak disk stays bounded by one output partition (NFR-TS03).
gcloud storage cat | funzip | duckdb → gs://05
Normalize · DuckDB as the streaming ETL engine

One COPY does read + normalize + write

COPY (
  SELECT SYM_ROOT              AS symbol,
         'quote'               AS event_type,
         DATE + TIME_M         AS ts,
         BID, BIDSIZ, ASK, ASKSIZ,          -- unified schema
         EX                    AS venue,
         'taq'                 AS source,
         QU_SEQNUM             AS seq,
         DATE                  AS dt
  FROM read_csv('/dev/stdin', header=true, auto_detect=true)  -- the pipe
  WHERE SYM_ROOT IS NOT NULL AND DATE IS NOT NULL AND TIME_M IS NOT NULL
)
TO 'gs://traderx-501015-tick-store/ticks'
   (FORMAT PARQUET, COMPRESSION ZSTD,
    PARTITION_BY (source, dt, symbol), OVERWRITE_OR_IGNORE true);
Proven tool, not a hand-rolled loader. DuckDB reads the un-seekable pipe in a single pass (can't count then copy), maps NYSE's CQ columns onto the same schema live capture uses, and writes partitioned ZSTD Parquet to GCS over its S3-compatible httpfs path.

  • Idempotent. A completed-list guard (.stage2-completed.txt) skips files already ingested — each run writes uniquely-named Parquet, so a naive rerun would duplicate rows.
  • The OOM outlier. 2025-03-11 (~39 GB) blew the 5 Gi limit — a separate retry job with DUCKDB_THREADS=2 + more memory brought it home. 28/28.
  • Digest-pinned images. Pinned by @sha256, not a reused tag, so nodes can't serve a stale cached build after a fix.
War story: funzip's harmless exit-noise tripped set -o pipefail → false FAILED → the job retry-looped → 12–23× duplicate partitions. Fix: key success on the normalizer's exit (PIPESTATUS[2]), not the pipe's. Wiped the dupes, kept the raw zips, re-ran clean.

THE PAYOFF · ONE QUERY, BOTH SOURCES

Real TAQ lands next to TraderX's own ticks

Because the normalizer targets the identical schema as live capture, ingested TAQ sits beside the platform's own ticks — every row tagged source (taq vs live). One DuckDB-over-Parquet query spans both.

// read_parquet(hive_partitioning=true) reconstructs source/dt/symbol as columns
source=taq   dt=2025-02-03  symbol=IBM   event_type=quote   (NYSE Consolidated Quotes)
source=live  dt=2026-07-…   symbol=IBM   event_type=trade   (TraderX pricing bus)

VWAP · daily-return · quoted-spread recipes  →  one store, one query, no per-source code

Takeaway

Transport once, normalize forever

What made it work

the two insights

Auth with what already works (browser cookies over WebDAV) instead of fighting the OAuth policy; and move the compute to the data (a GCE VM in-region, parallel streams). Then a disk-bounded DuckDB pipe does the rest.

The one honest caveat

cookie lifetime

Session cookies expire in a few hours — perfect for a one-shot bulk transfer that finishes inside one lifetime, not a standing scheduled sync. A recurring pipeline would still want the OAuth path (the pending IT consent).

The result: a disk-bounded, idempotent, in-cloud path that turns any NYSE TAQ drop into queryable Parquet — proven on ~650 GB, reusable for the next corpus without a line of new code.
